# STM32-Based Radar Target Detection and Threat-Zone Alert System
## Full Project Description, Problem Statement, Objectives, Hardware, Firmware Review, Progress and Testing
**Controller:** STM32F401CCU6 Black Pill  |  **Planned radar:** HLK-LD2450  |  **Optional visual component:** SG90 servo

## 1. Executive Summary
This project proposes a compact embedded surveillance and target-awareness prototype inspired by the general monitoring concept of radar surveillance systems. It is intended for academic demonstration of sensor interfacing, real-time embedded processing, configurable detection zones, status indication, user interaction, and fault handling. The selected controller is the STM32F401CCU6 Black Pill. The intended final sensor is the HLK-LD2450 24 GHz millimetre-wave radar module, which reports tracked-target information through a UART serial interface. Red and green LEDs and an active buzzer provide local status and alerts. A potentiometer can adjust a software-defined warning threshold. A push button can acknowledge an alert or pause/resume the demonstration. An LCD or laptop dashboard can display telemetry. The already purchased SG90 servo may be retained as a visual feature, powered from a separate regulated 5 V source, but it is not required for radar sensing.
The C program supplied with this request is an initial ultrasonic prototype, not final LD2450 firmware. It reads an HC-SR04 ultrasonic sensor, drives an SG90 servo, reads a potentiometer through ADC1, controls active-low LEDs, and transmits text over USART2. It is useful as a starting point for learning GPIO, ADC, timers/PWM, UART, and timing. It must be adapted before it can communicate with the LD2450. The radar version needs a UART receive implementation, the correct serial settings and packet parser, target-data validation, and application logic based on radar coordinates and speed. This document distinguishes existing code from planned work so that the report does not claim unimplemented functions as complete.
The system is a student-scale educational demonstrator. The LD2450 is intended for human-motion tracking and must not be represented as a general-purpose aircraft, jet, missile, or vehicle classification sensor. Any S-400 reference is visual inspiration only. The project does not include weapon control, firing, missile guidance, or autonomous engagement.

## 3. Problem Statement
Small embedded monitoring systems often need to detect a moving target, interpret sensor readings, compare those readings with a user-defined condition, and notify an operator without continuous manual observation. A simple indicator can show that a sensor state has changed, but a useful demonstrator should combine sensing, processing, configurable thresholds, user interaction, local alarms, and readable telemetry. It should also make the data path visible so the operator can understand why an alert occurred.
The problem addressed is the design of a low-cost educational prototype that integrates a microcontroller with a radar-based sensor interface and an alert subsystem. The system should receive target telemetry, validate incoming data, calculate or use target distance from sensor coordinates, compare a target against a configurable alert zone, and activate outputs when a configured condition is met. LEDs and a buzzer provide immediate local feedback; an LCD or laptop dashboard provides more detailed status. The prototype should be modular enough to compare the earlier ultrasonic approach with the planned radar implementation.
The engineering challenge is not merely connecting a sensor to a controller. The project must handle UART for radar data, ADC for the potentiometer, GPIO for LEDs and buttons, timer/PWM for the optional servo, and potentially I²C for an LCD. It must account for electrical voltage levels, power requirements, invalid data, timeouts, and the difference between moving-target tracking and stationary-object detection. The project demonstrates embedded-system integration rather than reproducing the performance of full-scale surveillance radar.
## 4. Motivation
The first motivation is to build a visible, interactive demonstration rather than a sensor that merely turns an LED on or off. A radar-style display, target coordinates, distance values, a configurable alert zone, and a buzzer/LED response make the processing pipeline easier to explain during faculty review. The work provides practical exposure to STM32 peripherals relevant to embedded engineering: GPIO, ADC, USART, timers, PWM, interrupts, and system timing.
The second motivation is to validate hardware choices before final assembly. The ultrasonic prototype offers a straightforward way to practise distance measurement and servo movement. The LD2450 uses a different sensing model: rather than returning a single echo-based distance, it sends a serial stream describing tracked targets. Comparing these approaches helps explain the difference between a low-cost single-distance sensor and a radar module designed to report multiple moving human targets.
The third motivation is modularity. By separating sensor-specific parsing from application logic, the same alert manager and display layer can remain in place even if the sensor changes. This makes debugging easier and reduces the amount of firmware that must be rewritten during a hardware change.
## 5. Novelty and Contribution
The project's novelty is at the level of system integration and educational demonstration, not the invention of a new radar technology. Its contribution is a compact platform that combines a radar data stream, configurable software zone, real-time embedded processing, local alert outputs, and a human-readable monitoring interface on an STM32F401. An ultrasonic prototype can be retained as a comparison mode.
The key contributions are: (1) a sensor-adapter approach that converts sensor-specific inputs into a common internal target representation; (2) a configurable alert zone whose threshold is adjusted by a potentiometer; (3) multi-output alerting through LEDs, buzzer, and display; (4) fault-aware processing for missing UART data, malformed frames, stale targets, and sensor disconnection; (5) a controlled indoor demonstration and dashboard that make target movement visible; and (6) documented pin mapping, power notes, and test cases for repeatable validation.
The LD2450 must not be claimed to identify an object as a car, aircraft, jet, or missile. Coordinates and motion telemetry alone do not establish an object's identity or class. The report should say "tracked target" or "moving human target" unless a separate, validated classification method exists.

## 9. System Overview and Architecture
The planned system has six layers. First, the LD2450 senses movement and processes radar reflections internally. Second, its UART interface sends target data to the STM32. Third, the receiver and parser validate incoming bytes and produce target records. Fourth, the target-processing module calculates or uses distance and applies the alert-zone rule. Fifth, an output manager controls LEDs, buzzer, LCD, and serial telemetry. Finally, a user interface displays state and allows the operator to adjust the threshold or acknowledge an alert.
The earlier ultrasonic prototype follows a different chain: the STM32 sends a trigger pulse to the HC-SR04, measures echo duration, converts duration to an approximate distance, moves the servo to a new angle, and compares the distance with the potentiometer threshold. This is useful as a baseline, but it does not receive LD2450 packets. The final firmware must not mix ultrasonic timing assumptions with radar UART parsing.
A common target record may contain target ID, detected flag, X coordinate, Y coordinate, distance, angle if derived, speed if provided, last-update timestamp, and validity. If the radar coordinate convention supplies X and Y in consistent units, distance can be calculated as sqrt(X² + Y²). Angle can be calculated using atan2 only after the module's axis order, units, and sign convention have been verified against its protocol and test data.
## 10. Hardware Specifications
STM32F401CCU6 Black Pill: the main controller. It provides GPIO, ADC, timers/PWM, USART, and other peripherals. It uses 3.3 V logic, so signal voltages must be checked carefully.
HLK-LD2450: the planned 24 GHz radar module. It provides target telemetry through UART. Confirm the exact board version, connector, supply rating, UART logic level, serial baud rate, and packet protocol from the actual product documentation before wiring.
SG90 servo: optional visual mount. It requires a PWM control signal and a suitable external 5 V supply. Do not use a GPIO pin or assume the STM32 3.3 V regulator can power it.
Red and green LEDs: status indicators. Each bare LED needs a current-limiting resistor. The supplied code uses active-low logic, so the physical wiring must match that assumption.
Active buzzer: audible alert. It can be driven directly only if voltage and current fit the STM32 GPIO limits; otherwise use a transistor or suitable driver.
10 kÎ© potentiometer: user-adjustable analogue input. Connect the ends to 3.3 V and GND and the wiper to an ADC-capable pin. Never feed 5 V into the ADC input.
Push button: acknowledge, pause/resume, or reset input. Use a pull-up or pull-down and software debouncing; use EXTI if an interrupt demonstration is required.
16Ã—2 LCD with I²C backpack: optional local display. Confirm the backpack's supply and I²C pull-up voltage. Some backpacks pull SDA/SCL up to 5 V, which can be unsafe for STM32 pins unless level compatibility is established.
Breadboard, jumper wires, regulated supply, and ST-Link: needed for safe prototyping and reliable programming/debugging. A pin map should be checked against the exact Black Pill schematic and STM32F401 alternate-function table before soldering.
## 11. Hardware Connections: Planned LD2450 Version
For a USART1 example, LD2450 TX connects to STM32 PA10/USART1_RX, and LD2450 RX connects to PA9/USART1_TX. UART signals are crossed: transmitter to receiver and receiver to transmitter. Connect LD2450 GND to STM32 GND. Connect VCC only after verifying the exact module's required supply. A separate UART-converter board is not normally required when the module exposes a compatible UART interface.
The red and green LEDs connect to free GPIO pins through resistors. The buzzer connects to a free GPIO through a suitable driver if its current exceeds safe GPIO capability. The potentiometer's ends connect to 3.3 V and GND; its wiper connects to an ADC input such as PA0 if that pin is otherwise available. The push button connects to a free GPIO with a defined pull-up/down. An LCD can use compatible I²C pins, for example PB9/PB8 if configured for I²C1, but the pin functions and pull-up voltage must be checked. The servo signal can use a timer PWM pin such as PA8/TIM1_CH1 if the selected configuration leaves it available. Servo power comes from an external regulated 5 V supply. Join the servo supply ground to STM32 ground.
These are candidate mappings, not a guarantee that all can be used simultaneously without conflicts. Maintain a pin-allocation table and check every alternate function before wiring. The exact LD2450 labels and supply requirements must be confirmed from the purchased board, not inferred from a marketplace title.
## 12. Power-Supply Design
The STM32 can normally be powered from laptop USB during development. That does not mean every peripheral should be powered from the MCU board. LEDs consume relatively little current but still need resistors. A small buzzer may need a transistor driver. An LCD may need 5 V or 3.3 V depending on its backpack, and its I²C pull-ups must be compatible with the STM32. The LD2450 must use the supply specified for the exact module.
The SG90 servo should use a regulated external 5 V supply capable of handling startup and mechanical-load current. Do not power it from a GPIO pin. Connect the servo signal to the selected PWM pin and join the servo supply ground to STM32 ground so the signal has a common reference. Do not connect two 5 V rails together unless the board's power architecture explicitly supports it.
For the first test, power the STM32 from USB and test one subsystem at a time. Confirm the radar supply rating, then connect radar ground and UART signals. Add LEDs with resistors, then the buzzer driver, potentiometer, display, and finally the servo. If the MCU resets when the servo moves, investigate supply droop and grounding rather than assuming the firmware is wrong.
## 13. Review of the Supplied C Code
The supplied code is a bare-metal register-level example for an STM32F4 family device. It initializes USART2 on PA2/PA3, ADC1 on PA0, TIM1 PWM on PA8, the HC-SR04 on PA6/PA7, and active-low LEDs on PA10/PA11. In the main loop it reads the potentiometer, maps ADC data to a threshold of 2-50 cm, updates servo angle, measures ultrasonic distance, updates the LEDs, and sends a text status line over USART2.
USART2_Init enables the USART2 peripheral and configures PA2/PA3 for alternate function 7. PA2 is TX and PA3 is RX for this mapping. BRR is set for approximately 9600 baud assuming a 16 MHz peripheral clock. The code enables transmitter and receiver, but the main loop only uses transmit helper functions. For the LD2450 version, a receive routine is essential, and serial settings must match the radar configuration.
ADC1_Init configures channel 0 on PA0. The potentiometer reading is scaled into a 2-50 cm threshold. This is useful for a configurable parameter, but the radar version should map the ADC value to a meaningful radar distance threshold in the units used by the parser, such as metres or millimetres.
Servo_Init configures TIM1 channel 1 on PA8. With a 16 MHz timer clock, prescaler 15 gives a 1 MHz timer count, and ARR 19999 gives a 20 ms period, approximately 50 Hz. The compare value maps -60 to +60 degrees into pulses around 1-2 ms. This is an approximate mapping and should be calibrated with the actual servo and mechanical mount. The servo should be described as a visual component in the radar version, not the mechanism that makes the LD2450 scan.
Ultrasonic_Init and Read_Distance configure PA6 as trigger and PA7 as echo. The program emits a trigger pulse, waits for the echo, counts its duration, and estimates distance using pulse-width divided by 58. It returns zero on timeout. This is a polling approach and depends on timing accuracy and clock assumptions. Importantly, HC-SR04 Echo commonly outputs 5 V while STM32 inputs use 3.3 V logic; use a voltage divider or appropriate level shifter unless the exact electrical specification confirms compatibility.
The LED functions assume active-low wiring: high means off and low means on. That is correct only if the LED anode is connected to 3.3 V through a resistor and the cathode to the GPIO. If the LED is wired from GPIO to ground, logic is normally active-high. Check the physical wiring and software polarity together.
The delay_us function reconfigures SysTick repeatedly and assumes a 16 MHz core clock. It is blocking and may interfere with other timing uses. The ultrasonic function also blocks while waiting for echo transitions. For the radar version, use interrupt- or DMA-based UART reception with a buffer so incoming data is not missed while the application waits or updates the display. Include timeouts and a stale-data timer to distinguish "no target" from "sensor communication fault."
## 14. Required Firmware Changes for LD2450
The firmware changes should be completed in order. First, confirm the exact LD2450 version, pin labels, supply rating, baud rate, and packet format from the manufacturer documentation. Second, select a hardware USART with available pins and check conflicts with the servo, LEDs, LCD, and ADC. Third, implement continuous UART reception, preferably with interrupts or DMA and a ring buffer. Fourth, parse the documented packet format exactly, including frame markers, length, coordinate representation, units, target slots, and any validation rules. Fifth, convert valid frames into structured target records and reject malformed or stale data.
The target-processing layer should calculate distance and angle only according to the documented coordinate system. The alert-zone logic should use a clearly defined condition, such as a valid target within a user-configured distance. The potentiometer mapping must match the threshold units. LEDs and buzzer should follow the application alert state, not the old ultrasonic distance variable. Telemetry sent to a laptop should use a documented human-readable format, separate from the radar's incoming binary protocol. Finally, implement a sensor timeout so that the absence of UART updates does not automatically appear as a safe condition.
A suitable firmware structure is: main.c; uart_radar.c/.h; ld2450_parser.c/.h; target_manager.c/.h; alert_manager.c/.h; adc_input.c/.h; gpio_outputs.c/.h; button.c/.h; lcd_display.c/.h; servo_demo.c/.h; and telemetry.c/.h. Keeping these responsibilities separate makes the program easier to test and explain during a viva.
## 15. Selecting a Target in a Busy Room
The LD2450 should not be described as a sensor that identifies arbitrary objects by name. It is intended for human-motion tracking and reports targets according to its tracking algorithm. In a room with multiple people or reflective surfaces, the module may report more than one target or behave differently because of movement and multipath. Stationary furniture is not reliably tracked as a moving target. For a clear demo, choose a controlled area, reduce unnecessary movement, and ask one person to move slowly across the test zone.
The application can select a record using a software policy-for example, the nearest valid target, a target inside a defined zone, or a selected target ID if the protocol provides a usable ID. This is a software selection policy, not a guarantee that the radar knows which physical object the user intended. Track IDs may change and targets can disappear, so the application must handle track loss and selection changes.
For faculty demonstration, mark a floor zone with tape and show three stages: no moving target in the zone, one person entering the zone, and the person leaving. Show the target data, threshold setting, status label, and LED/buzzer response. This is more repeatable than attempting to classify a toy car, jet model, or arbitrary object.

## 18. Test Plan and Expected Results
T01 Startup: power the STM32 and sensor. Until valid frames arrive, show an initializing or sensor-wait state rather than falsely showing "clear."
T02 UART healthy: valid radar frames arrive. Target records should update and the freshness timer should refresh.
T03 No moving target: the sensor reports no active target while communication remains healthy. The alert should be off, but the sensor should still be marked healthy.
T04 Target outside zone: a valid target lies beyond the threshold. The normal indicator should be on and the buzzer off.
T05 Target inside zone: a valid target lies inside the threshold. The alert indicator and buzzer should activate according to the configured rule.
T06 Potentiometer change: turn the potentiometer while a target moves. The displayed threshold should change smoothly and the alert logic should follow it.
T07 Target leaves zone: the target moves out of the configured zone. The alert should clear according to the chosen filtering or hysteresis rule.
T08 Multiple targets: more than one target is reported. The target list should be handled without mixing coordinates.
T09 UART disconnect: stop radar frames safely. The application should show sensor-fault/stale-data state rather than silently declaring the environment clear.
T10 Malformed data: feed invalid or incomplete data in a test harness. The parser should reject it and recover at the next valid frame.
T11 Servo test: run the servo from a separate regulated supply. The MCU should not reset or suffer excessive supply drop.
T12 Button debounce: press and release repeatedly. Each physical press should create one logical action rather than multiple toggles.
Record test ID, firmware version, sensor setup, threshold, observed values, expected behaviour, actual behaviour, pass/fail, and notes. Do not mark a test as passed until it has been physically or reliably simulated and documented.

## 20. Safety and Engineering Practices
Verify the exact LD2450 supply and UART logic levels before applying power. Never connect a 5 V signal directly to an STM32 input unless the specific pin is documented as 5 V tolerant and the configuration permits it. Use a resistor for every bare LED. Use a transistor driver if the buzzer current exceeds safe GPIO capability. Power the servo from a suitable regulated 5 V supply and share ground with the STM32. Avoid connecting external 5 V and board 5 V rails together without understanding the board's power-path design. Disconnect power before changing wiring. Secure the servo mount and keep fingers and wires away from moving parts. Use the radar for the stated indoor educational demonstration and respect the privacy of people in the test area.
## 21. Risks and Mitigation
Wrong module variant: the pinout or capabilities may differ. Mitigation: verify the model marking and manufacturer/seller documentation before wiring.
UART baud or protocol mismatch: no readable target data appears. Mitigation: use documented settings, inspect raw bytes, and test the parser independently.
Power instability: resets, corrupted data, or servo jitter occur. Mitigation: use a separate servo supply, common ground, and adequate current capacity.
Sensor does not report a stationary prop: the demo appears not to detect it. Mitigation: use a moving person and explain the sensor's intended tracking behaviour.
Busy room or multiple tracks: target selection becomes confusing. Mitigation: create a marked demo zone and define a software selection rule.
Stale UART data appears safe: the system may falsely show clear. Mitigation: implement a freshness timeout and explicit sensor-fault state.
Pin conflicts: peripherals interfere. Mitigation: maintain a pin map and check alternate functions before final wiring.
Overclaiming capability: faculty may challenge unsupported claims. Mitigation: describe the project as human-motion radar tracking and zone-based alerts, not aircraft or vehicle classification.
## 22. Future Improvements

The servo can be retained for appearance, but it does not cause the LD2450 to electronically scan.
